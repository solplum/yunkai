# 云开下一版：以实际办事结果为目标

## 产品目标

用户交代目标后，助手能在真实手机应用中完成任务，提供可核对的结果；遇到异常会重新观察或明确停下；必须接管时说清原因。不是追求工具数量、改动行数、纯本地宣传或保留旧代码。

## 技术决定

以固定版本 Mika 的完整 Android 任务与手机操控链为下一版基础，放在 `yunkai-next/`。保留 shell 助手、后台虚拟屏、无障碍/OCR/视觉定位、输入路径、动作读回、接管与生命周期清理的组合，不先拆散后再自行重建。

旧 `yunkai-android/`、`yunkai-harmony/` 不覆盖；下一版使用独立 applicationId。保留命名空间是避免破坏反射/AIDL/助手入口的技术措施，不代表伪装成上游发布。归属、许可和修改见 `UPSTREAM.md`。

独立目录是验证隔离阶段，不是长期维护两套 Android 产品的目标。证明新底座有效后，再决定旧 Android 功能的迁移和退役；现有数据必须有显式、可预览的导入路径。

## 先验证什么

| 场景 | 成功证据 | 失败时应怎样 |
| --- | --- | --- |
| 打开应用，找到指定内容 | 前台/目标显示器确为目标 App；详情标题或标识匹配 | 目标缺失、重名或窗口改变时停止旧动作，不猜目标 |
| 跨页面填写草稿 | 进入复核页后完整读回两处输入，内容一致 | 输入接口返回成功但内容未出现，不能算完成或继续发送 |
| 弹窗、慢加载、目标变动 | 新观察识别当前界面，再继续明确可执行的步骤 | 不沿用旧坐标；说明已做/未做与需要接手的原因 |
| 操作结果不确定 | 只有明确回执才记成功 | 不自动重复外发动作，不把未知当失败重试 |
| 后台独立屏 | 目标显示器动作正确，主屏交互不被误操作 | 焦点/显示器不可保证时明示限制或停下 |

优先使用专用测试应用与合成内容，不用用户私聊、账号资产或真实发送来试错。真实设备测试前单独取得设备和权限授权。模型调用成本与真实账号操作也不得由这份计划推定授权。

## 验证分层，不能互相替代

1. 源码完整性与许可证、安装身份隔离检查。
2. 真实引擎配模拟设备边界的 JVM 测试：验证调度、选择、读回与停止逻辑，不验证 Android 实现。
3. Android 构建和安装测试：验证组件、资源、AIDL、依赖与 APK，不等于真实 App 任务成功。
4. 授权测试机上的真实操作：记录型号、系统/应用版本、前后画面和成功/失败原因；先重复基本任务，再扩大到复杂自绘应用。
5. 只有端到端证据支持时才宣称某类任务可用。不得以导入上游、测试总数或模型自称成功替代该证据。

## 当前明确未交付

- 并非已验证可用的云开新版 APK；当前为迁移原型。
- 原云开的记忆、个人技能、历史、模型凭据尚未迁移。
- 上游宽松审批、自动恢复设置以及第三方 runtime 分发义务需在发布前审查，不能默默扩大权限。
- 基线测试发现 `phone_run` 仅有子串匹配时可能选中近似项。本轮对 tap/type/clear 的 `targetText` 改为默认完整名称匹配，模糊标签需要显式 `textMatch=contains`；该修复不代表所有工具、视觉目标或结果断言都获得精确身份保障。
- Android SDK 许可与安装授权待确认；不因此停止可独立进行的源码与 JVM 验证。

后续开发顺序由上述验收结果决定。优先修阻碍完成任务的环节，再迁必要的云开能力；不在底座未验证时先做界面翻新或堆砌功能。
